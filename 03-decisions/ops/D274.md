**D274 (LOCKED Session 379)** — Sentry is the error-reporting layer, superseding D62's log-only ruling and closing D266 part 1. D62 decided in Session ~150 that alarms would be error-level log lines only, with no Sentry dependency and `SENTRY_DSN` named as an optional hook, on the reasoning that a Railway log monitor watching a dedicated event name was sufficient for MVP. That reasoning was sound when nothing ran unattended. It is no longer: three services now run without a human watching, the frequent-jobs cron fires every ten minutes and touches the money path through the post-window sweeper, and the observed consequence of having no watcher is on record twice — the sweeper `underfunded` loop ran broken for weeks (D266), and the 15 July listing-expiry fix sat committed and undeployed for six days (M36). `backend/app/observability.py` holds three functions: `init_sentry(component)`, `capture_exception(exc, **tags)` and `flush_sentry()`. It is a no-op when `SENTRY_DSN` is unset, so nothing changes for a developer without the variable. The API initialises it in `main.py` and calls `capture_exception` from the global exception handler; both cron runners initialise it, call `capture_exception` per failed job with a `job` tag, and call `flush_sentry()` in their `finally` blocks — the explicit captures are required because both runners catch every exception and log it, so nothing ever propagates to where the SDK would notice on its own. Two configuration rulings, both made after observing real behaviour rather than in advance. First, the SDK is initialised with `LoggingIntegration(event_level=None)`: by default any `logger.error` or `logger.exception` becomes an issue, and a pytest run demonstrated that this turns deliberately handled conditions — `Payment setup failed`, `AI service temporarily unavailable`, `Strike enforcement failed` — into alerts, which would exhaust a 5,000-event monthly allowance on normal operation and train the operator to ignore the feed. Consequence to hold: from now on only unhandled crashes and explicit `capture_exception` calls produce issues, so anything that must be reported has to be captured deliberately. Second, `init_sentry` returns immediately when `pytest` is in `sys.modules`, because `.env.local` now carries the DSN and a local test run was observed sending eight issues. Verified end to end rather than assumed: a temporary throwing route was deployed to production (`6e84635`), hit once, confirmed as a `production`-tagged issue in Sentry, and removed (`d571242`); a short-lived process was confirmed to deliver, which proves the cron path; and after the two guards, a full suite run moved no event count. Project `python-fastapi` under org `zelbi`, free tier, GitHub integration installed scoped to the `zelbi` repo only. The DSN lives in [secrets manager] dev and prd per M37. Not covered, deliberately: the metrics dashboard (D266 part 3) remains unscheduled, and the mobile app has no Sentry project. Commits `893bd47` and `cc82e0f`.
