D442 — LOCKED (2026-09-02, Session 437). RATE-LIMIT CEILINGS STAY; A HIT IS AN ADMIN SIGNAL, NOT A USER-FACING BUG. Nick's ruling: the per-user ceilings (uploads 60/h, AI analysis 60/h, claim creation 30/h, Places 600/h, knowledge 30/h per address — D275 and its Session 379 extension) stay exactly as set. They exist to stop scripts, not people; a real person is not expected to reach them, and whether someone who does is a mover or a spammer cannot be known at the moment it happens, so the app neither raises a ceiling nor hides or rewords the refusal. Instead the dashboard arc (D325) gains an obligation: every rate_limit_exceeded event is surfaced per user so an admin can watch a repeat offender and act. No phone change, no backend change. CORRECTS the record: backlog row 29's "the app renders a 429 as an empty list" described the claims READ limit, which moved onto claim creation alone on 2026-08-13; since then no list endpoint is limited, so that symptom cannot occur. The listings feed remains unlimited by design. Today a limit hit is a log line only — Sentry reports crashes and explicit captures per D274 — so the alert does not exist until the dashboard builds it.
