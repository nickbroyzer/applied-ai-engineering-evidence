**D275 (LOCKED Session 379)** — Per-user rate limiting exists on the AI router only, held in process. `backend/app/rate_limit.py` provides a `rate_limit(name, limit, window_seconds)` dependency factory over a per-user sliding window kept in a module-level dict guarded by a lock; exceeding it raises 429 with a `Retry-After` header and logs `rate_limit_exceeded`. It is applied at router-include level in `main.py` to the AI router, covering `analyze-photo` and `check-readability` — the two endpoints that spend Anthropic credits per call — at 60 calls per user per hour. A move-out giver posting twenty items with retries stays far under that ceiling; a script hits it in about a minute. No Redis and no Upstash: the Railway web service runs at one replica (verified), so an in-process counter is exact, costs nothing, adds no vendor and no network hop. Consequence to hold: the counter is per-process and resets on every deploy, and if the service is ever scaled to multiple replicas the effective limit multiplies by the replica count and the store must move to Redis — a small change, but one that must happen at the moment of scaling, not after. Verified by exercising the window directly: 60 allowed, 61st blocked, retry window correct, a second user unaffected. Known gaps, none closed by this entry: the limit is per user and account creation is still unthrottled and unfingerprinted (D271), so many accounts multiply the budget; uploads, claim creation and the Google Places endpoint have no ceiling; nothing watches Anthropic spend, and a console-side spend cap is the only hard stop; and mobile has no 429 handling, so a tripped limit surfaces as the give-flow's generic error.
